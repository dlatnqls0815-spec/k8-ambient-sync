# 기술 결정

## 2026-11-07 — 관측이 제어보다 먼저
순정 조명에 쓰지 않는다. HMG-API `LightRelay`의 방송 수신 경로를 조사하되
공개 vehicle API가 ambient 구독을 제공한다고 가정하지 않는다.
16비트 RGB에는 테마 코드가 포함될 수 있으므로 8비트 잘라내기/정규화를 금지한다.

## 2026-11-07 — Java 7 코어, 모의 transport
HMG-API는 Java/API19 환경이다. 코어는 Android 의존 없이 같은 언어로 검증한다.
PC의 파일 저장 유틸리티는 host에 분리한다. 실제 장치 transport는 작성하지 않는다.
공개 Lotus 후보는 이름을 붙여 구분하고, 후보 패킷 테스트가 K8 장치 검증을 의미하지 않음을 명시한다.

## 2026-11-07 — 직접 연결 우선, 장비 구매 보류
Gen5W BLE 미확인 상태에서 Galaxy 또는 ESP32를 필수로 만들지 않는다.
200ms는 실측 목표이며 모의 시계 테스트의 숫자로 달성했다고 주장하지 않는다.

## 2026-11-07 — 로컬 작업
첫 세션에서는 기존 Git 인증으로 비공개 빈 저장소를 확인했고 사용자 답변에 따라 Push하지 않았다.
main에 초기 기준을 만들고 기능은 codex 브랜치에서 진행한다.
기존 Codex/GitHub 로그인이나 전역 Git 설정은 바꾸지 않는다.

## 2026-11-07 — GitHub 동기화 재개
사용자가 GitHub 로그인 완료를 알렸다. 원래 지시서의 원격 Push 요청을 재개한다.
인증된 계정의 저장소 쓰기 권한, private 상태와 원격 브랜치 부재를 다시 확인했다.
초기 main과 기능 브랜치만 명시적으로 일반 Push한다. main에 구현을 병합하거나 강제 Push하지 않는다.
기존 179개 검사/API19 계약 컴파일 이후 실행 코드는 바뀌지 않아 같은 검사는 반복하지 않는다.

## 2026-11-07 — 라이선스와 경계
새 코드는 HMG 연동을 고려해 AGPL version 3로 통일한다(`LICENSE`, `NOTICE.md`).
외부 구현을 복사하지 않고 공개 인터페이스/패킷 사실만 독자 구현한다.
라이선스 미확인 코드·팔레트는 사용하지 않는다. 원본 소스와 빌드 의존성은 커밋하지 않는다.

## 2026-11-07 — 실제 Galaxy 자료 단계
사용자가 무선 디버깅을 요청했다. 기존 페어링의 표준 ADB mDNS 광고로 재연결한 뒤
Samsung/API/비차량 조건을 확인하고 고정 Lotus 패키지의 OS·버전 메타데이터만 읽었다.
실제 값은 Android 17/API37, LotusLamp X 5.21.03(425)다.
base APK는 로컬 private에만 복사했다. 앱 실행·설정 변경·기기 키/계정/앱 데이터 읽기는 하지 않았다.
차량·조명은 현재 접근 불가하므로 HCI 실측을 다음 정차 시험으로 남긴다.

## 2026-11-07 — HCI 분석 범위
HCI/L2CAP 재조립을 새로 구현하지 않고 TShark의 선별 필드 TSV를 읽는다.
버전·헤더·값·범위·세션을 검증하고 후보 형식의 정규화 값만 남긴다.
원본 ATT payload와 식별자·경로를 출력하지 않으며 결과 파일은 private에만 쓴다.
후보 일치만으로 프로토콜·UUID·LE/Classic·조명 반영·ACK를 확정하지 않는다.
도구가 TShark를 설치하거나 캡처·Bluetooth 송신을 자동 실행하지 않는다.

## 2026-11-07 — 설치본의 여러 프로토콜
실제 5.21.03 base APK에 E1/E2 builder와 조건부 암호화 분기가 존재함을 정적으로 확인했다.
RGB 일부의 일치로 밝기·전원·초기화까지 일치한다고 판단하지 않는다.
기존 후보 코덱은 모의 전용으로 유지하고 실제 HCI/조명 반응으로 대상 분기를 확인한 뒤 연동한다.

## 2026-11-08 — A안 종료, B안(Galaxy 중계) 구현
차량 Bluetooth 스택(`bplus.default.so`)에 GATT 클라이언트가 없어 A안을 닫았다([근거](research/K8_BLE_GATT_DISABLED.md)).
사용자가 B안을 선택했다(ESP32 C안은 추후 구매 예정).
차량은 순정 로그의 SML 상태를 **읽기만** 하고, 클래식 RFCOMM 서버로 원시 상태만 보낸다. 차량 명령은 없다.
휴대폰이 조명에 실제 BLE 쓰기를 한다. 색상·밝기 프레임은 HCI로 실측한 형식이라 실제 송신을 허용한다.
전원 프레임은 앱 바이트코드 근거만 있어 기본 꺼짐 옵션으로만 둔다(HCI 대조 후 기본값 재검토).
상태 요청(`requestSMLStatus`)은 보내지 않는다. 시동 직후 첫 동기화는 로그 버퍼에 남은 마지막 상태나 첫 변경에 의존한다.

## 2026-11-08 — 전원 프레임 실제 반응 확인
앱 바이트코드에서 읽은 Lotus 전원 프레임이 실제 조명에서 꺼짐·켜짐으로 동작함을 사용자가 확인했다.
HCI 대조는 아니지만 동작 근거가 생겼다. 휴대폰 앱의 전원 옵션은 아직 기본 꺼짐으로 두고,
다음 앱 버전에서 기본 켜짐으로 바꿀지 사용자와 정한다.

## 2026-11-17 — C안 전환: ESP32가 조명 구동, 휴대폰은 설정 전달
사용자 요청: "ESP32 연결했거든 … 엠비언트라이트 연동을 ESP로 … 휴대폰은 ESP32로 색상및 밝기 어플이 하던 셋팅을 넘겨받는 용도".
보드는 일반 ESP32 WROOM-32D(CP2102 USB, 클래식 BT·BLE 모두 지원)라 2026-11-08의 S3 제약은 해당하지 않는다.

- **차량 → ESP32: 기존 통로(클래식 RFCOMM) 그대로.** 차량 중계 0.4.0이 기존 휴대폰 서비스("K8 Ambient Relay", 전용 UUID, 보안 연결)는
  유지하고, 같은 줄 프로토콜(`K8AMB 1`, `SML`, `MODE`, `ALERT`, `PING`)을 두 번째 서비스 **"K8 Ambient ESP32"**로도 보낸다.
  - UUID는 표준 SPP `00001101-…`: ESP32(Arduino BluetoothSerial/IDF)의 SDP 탐색은 SPP UUID 레코드만 찾는다. 이름으로 우리 서비스를 고르고,
    연결 직후 `K8AMB 1` 인사가 없으면 다른 채널로 넘어간다. 수동 채널 지정(`SET carch n`, 시리얼 전용)도 둔다.
  - **비보안(insecure) 서비스**: 헤드유닛에는 휴대폰이 아닌 기기를 페어링할 흐름이 없을 가능성이 크다. 이 통로는 읽기 전용 상태만 보내고
    명령을 받지 않으므로 본딩 없이 연다. 헤드유닛 스택(bplus)이 비보안 서버·SPP UUID 레코드·두 번째 ACL을 허용하는지는 **실차 미확인**.
  - 차량 명령은 여전히 없다. 차량 쪽 변경은 중계 패키지 설치뿐(사용자 승인 후).
  - Wi-Fi·USB 시리얼 대안은 헤드유닛 쪽에 새 통로(핫스팟/USB 호스트 권한)가 필요해 기존 근거가 있는 RFCOMM을 택했다.
- **ESP32 → 조명: BLE 중앙(central).** 휴대폰 0.4.8의 계산(K8LotusMapping·DriveModeLight·ColorTone·HueBrightness·Fader·SyncEngine·
  Lotus/Zengge 프레임, 경고·복귀 페이드)을 C++(`esp32/k8amb_esp32/k8core.*`)로 그대로 옮겼다. 같은 입력에 같은 결과인지
  Java 코어가 만든 기대값(`EspGolden`)과 보드의 `CALC` 응답을 비교한다(`tools/esp32_serial_check.py`).
  - **조명 쓰기는 기본 꺼짐(`output 0`)**: 이때 프레임은 USB 시리얼에 `TX lotus|zengge <hex>`로만 찍힌다. 조명 BLE 쓰기 시험은
    사용자 승인 후 휴대폰의 "ESP32가 조명에 실제로 쓰기" 또는 시리얼 `SET output 1`로 켠다.
  - 조명은 한 번에 한 중앙만 받으므로 ESP32 모드에서 휴대폰 중계는 시작하지 않는다(자동 시작 포함).
- **휴대폰 → ESP32: BLE GATT 설정 서비스.** ESP32가 "K8AMB-ESP32"로 광고, 서비스 `6b38a0d2-…-2e8f71c3b9e0`,
  쓰기 `…b9e1`(한 줄 한 쓰기, 응답 있는 쓰기), 알림 `…b9e2`(`OK`/`ERR`/`CFG`/`ST` 줄). 휴대폰은 MTU 247을 요청한다.
  - 줄: `SET car|lotus|zengge <주소|->`, `SET order GRB`, `SET power 0|1`, `SET fade|gamma|red|green|blue|lotusMax|zenggeMax <n>`,
    `SET hue a,b,c,d,e,f`, `SET eco|sport r,g,b`, `THEMES CLEAR`, `THEME <12hex> r,g,b|-`, `SAVE`, `SET output 0|1`, `GET`, `STATUS`.
    형식은 core `EspConfig`(테스트 포함)가 만들고 ESP32가 범위를 다시 검사한다. `SAVE`에서 NVS에 저장(설정 글 그대로).
  - 휴대폰 앱 0.5.0: "ESP32 모드"(기본 꺼짐 — 업데이트만으로 지금 되는 B안이 깨지지 않게), ESP32 찾기, 설정 자동 전달(슬라이더·색·테마·조명 선택 변경 시),
    ESP32 상태 표시(차량 연결·조명·현재 테마 키). 테마 색 지정은 ESP32가 보고한 현재 테마 키를 쓴다.
  - 설정 서비스는 인증이 없다(근처의 누구나 색 설정을 바꿀 수 있음). 위험이 조명 색에 한정돼 첫 버전은 그대로 두고 실차 확인 후 재검토.
- 같은 USB 시리얼 줄로 PC에서 모든 기능을 확인한다: `SML/MODE/ALERT` 모의 입력(시리얼 전용), `CALC`, `STATUS`, `GET`.
