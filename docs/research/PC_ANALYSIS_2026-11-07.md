# PC 재분석 — 2026-11-07 (Claude)

차량에 다시 가기 전에 노트북의 기존 자료만으로 진행했다. 차량·휴대폰·조명에는 접속하지 않았다.
원본 APK·로그·HCI는 `private/`에 그대로 있고 이 문서에는 주소·serial을 적지 않는다.

## 1. 진단 APK 설치 오류

### PC 검사 결과

| 검사 | 원래 v1/v2 APK | legacy v1 APK |
|---|---|---|
| ZIP 항목 | AndroidManifest.xml, classes.dex, META-INF 3개. 중복·암호화·데이터 디스크립터 없음 | 동일 |
| MANIFEST.MF 항목 다이제스트 | SHA-256, 두 항목 모두 실제 내용과 일치 | SHA-1, 두 항목 모두 일치 |
| .SF의 Manifest·섹션 다이제스트 | 모두 일치 | 모두 일치 |
| PKCS#7 서명(.RSA → .SF) | OpenSSL 검증 성공 | OpenSSL 검증 성공 |
| SignerInfo 형식 | issuerAndSerialNumber, SHA-256, sha256WithRSA | issuerAndSerialNumber, SHA-1, rsaEncryption, 서명 속성 없음 |
| 서명자 수 | 1명, 인증서 1개 | 1명, 인증서 1개 |

legacy APK는 KitKat 이전부터 쓰던 고전 v1 형식 그대로다. 두 APK는 PC 기준으로 정상이다.

### 해석

순정 Android 4.4의 `PackageParser.collectCertificates()`가 `INSTALL_PARSE_FAILED_INCONSISTENT_CERTIFICATES`를
돌려주는 경로는 **META-INF 밖의 항목끼리 서명자 집합이 다를 때**다. 서명 블록을 못 읽거나
서명이 깨지면 순정 코드는 `NO_CERTIFICATES` 쪽으로 간다. 이 APK에는 서명 대상 항목이 두 개뿐이고
둘 다 같은 단일 서명자로 검증되므로, 순정 파서에서 이 오류가 나올 조건이 보이지 않는다.
서명 형식이 다른 두 APK가 **똑같은 오류**로 거부된 점도 서명 형식 문제가 아님을 뒷받침한다.

따라서 현재 가장 유력한 원인은 **제조사가 수정한 패키지 관리자의 설치 정책**(서명 허용 목록 등)이다.
HMG-API 맵(framework.json 등)에는 PackageManager 관련 클래스가 없어 HMG-API Hook이 원인일 근거는 없다.
공개 Gen5W 분석 자료도 일반 설치 대신 `/system/priv-app` 배치를 사용하며 과거에 서드파티 APK가
막혀 있었다고 언급한다. 이것은 강한 정황이지만 **차량 로그로 확정한 것은 아니다.**

결론: **서명 형식·키를 바꿔 다시 빌드하는 시도는 중단한다.** 같은 결과가 반복될 가능성이 높다.

### 원인을 좁히는 데 필요한 추가 자료

두 APK의 설치 시도와 거부는 이미 완료됐다. 당시 PackageParser/PackageManager 로그는 보존되지 않았다.
원인을 더 좁혀야 할 때만, 승인 범위에서 다음처럼 설치 1회와 로그 읽기를 함께 한다.
로그 삭제(`logcat -c`)는 하지 않는다.

```powershell
adb -s <차량> install private/ble-diagnostic/gen5w-ble-diagnostic-legacy.apk
adb -s <차량> logcat -d -v time -s PackageParser:V PackageManager:V > private/vehicle-adb/install-logcat.txt
```

- `has mismatched certificates at entry`가 있으면 순정 경로다. 해당 항목명을 보고 다시 분석한다.
- 이 문구가 없다는 사실만으로 제조사 정책을 확정하지 않는다. 제조사 고유 문구·허용 목록 같은
  **직접 근거**가 있을 때만 OEM 정책으로 판단한다.
- 선택: 차량의 `/system/framework/services.jar`·`services.odex`를 `adb pull`로 읽어 오면
  PC에서 `-104`를 설정하는 위치를 정적으로 찾을 수 있다. 읽기 전용이지만 별도 승인 후 진행한다.

### 설치 없이 직접 BLE를 시험하는 대안(모두 별도 승인 필요)

| 방법 | 장점 | 위험·확인할 것 |
|---|---|---|
| 같은 점검 코드를 DEX로 만들어 `app_process`로 셸 권한에서 실행 | 패키지 설치가 필요 없음. 시스템 파일 변경 없음 | KitKat 셸 UID에 BLUETOOTH 권한이 있는지 먼저 `dumpsys package com.android.shell`로 확인 |
| `/system/priv-app` 배치 | 공개 자료에서 사용한 방법 | 시스템 파티션 변경. AGENTS 규칙상 별도 승인·백업·롤백 필수. 권장하지 않음 |
| HMG-API 모듈로 실행 | 기존 Hook 환경 재사용 | 다른 모듈 설치에 해당. 별도 승인 범위 |

## 2. K8 순정 SML 로그 재분석

### 정적 분석으로 확인한 송신 형식

`automotive-service` DEX의 `SystemService`에서 다음을 확인했다.

- `setSMLConfiguration(mode, data)`는 `[mode & 0xff, data & 0xff]` 2바이트를 명령 `0x15E(350)`로 보낸다.
- `setSMLRGB(red[], green[], blue[])`는 호출자가 준 바이트 배열을 그대로 6바이트 버퍼에 넣어
  명령 `0x15F(351)`로 보낸다. **16비트 값과 상위 바이트는 SystemService가 아니라 호출 앱이 만든다.**
  팔레트·테마 의미는 호출 앱(로그의 `called by` 프로세스, 설정 화면 앱) 분석이 필요하다.
- 응답 처리 후 `com.mobis.intent.action.SML_STATUS_CHANGED` 방송을 보낸다.

### 밝기 raw 1의 의미

| 수집 | mode=5 data 순서 | 사용자 조작 |
|---|---|---|
| 최초 39줄 | 1, 3, 4, 8, 7, 11 | "꺼짐 후 1단계를 누르니 켜졌다" |
| 추가 22줄 | **1, 2**, (RGB), 3, 4, 5, …, 11 | 계획된 순서 "꺼짐 → 켜짐 1단계" 후 색상 선택 |

추가 수집은 계획된 조작 순서와 정확히 맞는다: **꺼짐=1, 1단계=2**, 이후 3~11은 2~10단계다.
최초 수집에는 2가 없고 1 다음이 3이다. 사용자가 꺼짐 뒤 누른 단계가 실제로는 2단계였다면
두 수집 모두 `raw1=꺼짐, raw2~11=1~10단계`로 일관되게 설명된다. 이는 기존 EV6 참조 규칙과도 같다.

- 응답 9바이트 중 8·9번째 바이트는 꺼짐 요청 뒤에도 항상 `0x01`이었다.
  전원 상태는 별도 바이트가 아니라 밝기 값 1 자체로 표현되는 것으로 보인다.
- **판단:** `raw1=OFF`가 현재 가장 유력하다. 실제 소등을 눈으로 확인한 기록은 없으므로 코드의
  임시 함수는 아직 바꾸지 않았다. 확정되면 `raw2..11 → 1..10단계 → 사제 2..20%`(단계×2%)가 자연스럽다.
  현재 함수는 raw1을 2%로 켜므로, raw1이 OFF라면 꺼야 할 때 조명을 켜는 방향의 오류가 생긴다.

### RGB 상위 바이트

| 순서 | 16비트 R,G,B | 상위 바이트 | 하위 바이트를 RGB로 본 색 |
|---|---|---|---|
| 1차 1 | 383, 410, 378 | 모두 0x01 | #7F9A7A 탁한 초록 |
| 1차 2 | 335, 394, 451 | 모두 0x01 | #4F8AC3 탁한 파랑 |
| 1차 3 | 423, 354, 383 | 모두 0x01 | #A7627F 탁한 장미색 |
| 1차 4 | 250, 4, 81 | 모두 0x00 | #FA0451 선명한 빨강 |
| 1차 5 | 132, 229, 98 | 모두 0x00 | #84E562 선명한 초록 |
| 1차 6 | 16, 32, 239 | 모두 0x00 | #1020EF 선명한 파랑 |
| 1차 7(복원) | 363, 346, 405 | 모두 0x01 | #6B5A95 탁한 보라 |
| 2차(선택) | 155, 33, 239 | 모두 0x00 | #9B21EF 선명한 보라 |

8개 모두 세 채널의 상위 바이트가 **같은 값**(전부 0 또는 전부 1)이다. 상위 1 그룹은 모두 채널 최솟값이
335 이상이고 상위 0 그룹은 모두 최댓값이 250 이하다. 연속 9비트 밝기 값이라면 섞인 경우가 나올 법한데
나오지 않았다. 그래서 **상위 바이트 0x01은 "테마/프리셋" 구분 플래그, 0x00은 직접색**이라는 가설이
유력하다. 다만 표본이 8개이고 실제 발광색과의 대응은 미확인이다.

평소 설정(1차 복원값이자 2차 시작값)은 상위 1 그룹의 #6B5A95 보라다. 드림퍼플이 테마라면 이 값이
드림퍼플일 가능성이 있다. 반면 2차에서 고른 값은 상위 0 그룹의 #9B21EF 보라다.
**사용자에게 물어서 차에 가지 않고 정리할 수 있는 질문:**
평소 설정이 테마 목록의 드림퍼플인지, 2차에서 고른 것이 테마였는지 직접색이었는지,
원래 설정 복원이 감시 종료(약 5분) 뒤였는지.

변환은 계속 보류한다. 상위 바이트를 버리거나 0~255로 잘라 쓰지 않는다.

## 3. Galaxy HCI 재검토

### 최초 캡처(색상·밝기 확인분)

BTSnoop 시각은 기기 현지 시각으로 보인다. 아래 근거로 확인했다.

- **연결 직후 미확인 쓰기 `7e 06 83 10 36 35 06 00 ef`는 시계 동기화로 보인다.**
  `0x10 0x36 0x35`=16:54:53이고 HCI 기록 시각 16:54:53과 일치한다. `0x06`은 토요일(2026-11-07)과 맞는다.
- 색상 프레임은 `7e 07 05 03 RR GG BB 10 ef`다. 빨강·초록·파랑 뒤 복원값은 `7e 00 ff`(보라)였다.
- "별도 연결의 6개" 쓰기는 **조명과 다른 기기**다. 주소가 다르고, CCCD 활성화(`02 00`)와
  16바이트 난수형 값만 있다. LotusLamp 분석 대상에서 제외한다.

### 추가 USB 보고서의 ATT 쓰기 0건

| 파일 | 시각 범위(현지) | 조명 연결 |
|---|---|---|
| `btsnoop_hci.log.last` | 20:19:22 ~ 20:40:53 | LE 연결 없음 |
| `btsnoop_hci.log` | 20:41:34 ~ 20:47:25 | LE 연결 1건. 휴대폰이 주변기기 역할이고 상대가 휴대폰 GATT를 읽음. 조명 아님 |

정차 수집 파일 시각은 19:33~19:40이다. Lotus 조작도 그 무렵이었다면 **조작 구간이 남은 두 로그보다
앞서서 순환으로 사라진 것**이다. 0건은 "전원 명령 없음"이 아니라 "조작 구간 미수집"이다.
다음에는 조작 직후 차 안에서 바로 버그 보고서를 만들고, 보고서 전에 블루투스를 끄고 켜지 않는다.

## 3-1. 사용자 답변 반영 (21:39)

| 질문 | 답 | 결과 |
|---|---|---|
| 평소 순정 테마 | 드림퍼플 | 1차 복원값이자 2차 시작값 `0x016b 0x015a 0x0195`(상위 0x01)가 **드림퍼플 테마**로 대응된다 |
| 2차에서 고른 색 | 더 자주 쓰는, 푸른빛이 조금 더 도는 보라 | `0x009b 0x0021 0x00ef`(상위 0x00, #9B21EF)는 **직접색**이다 |
| 복원 시점 | 감시 중, 약 10초 뒤 | 그런데 2차 로그에는 복원 RGB 요청이 **없다** |

- 상위 바이트 가설은 테마 1건·직접색 1건이 사용자 답과 맞아 강해졌다: **0x01=테마, 0x00=직접색**.
  다른 테마 3개(1차 앞부분)는 어떤 테마인지 이름이 없어 대응표는 드림퍼플 하나만 확정 후보다.
- 복원이 로그에 없는 점은 미해결이다. 가능성: 복원이 RGB가 아닌 다른 경로(테마 재선택이 이미 저장된
  값을 MICOM이 직접 불러오는 등)로 처리됐거나, 사용자가 되돌린 대상이 밝기였을 수 있다.
  PC에서 OEM 분석으로 테마 복원 경로를 먼저 찾는다. 현장 기록은 PC로 답하지 못할 때만 정한다.
- 직접색 하위 바이트를 그대로 Lotus RGB로 쓰는 변환은 아직 하지 않는다. 테마의 하위 바이트(#6B5A95)는
  대표색일 뿐 실제 발광과 같은지 미확인이다.

## 3-2. Lotus 전원 명령 후보 (정적 분석 + 실측 결합)

기존 [설치본 분석](LOTUS_APK_5_21_03.md)과 최초 HCI 실측을 합치면 다음이 성립한다.

- 실측 밝기 120개는 모두 `7e 04 01 <lv> 01 ff 02 01 ef`이고 끝 두 바이트 `02 01`이 항상 같다.
  정적 분석의 밝기 payload 순서(값·lamp type·`FF`·appType·appVersion)와 대응하면
  **이 조명 분기의 appType=0x02, appVersion=0x01**이다.

### APK 바이트코드 재확인 (21:44, 사용자 제공 APK)

사용자가 올린 APK의 SHA-256이 기존 기록 `d0eca36d…49e2`와 같다. 설치된 도구가 없어 작은 DEX 역어셈블러로
`classes2.dex`의 해당 메서드만 읽었다. 앱을 실행하거나 조명에 보내지 않았다.

| 메서드 (code_item) | 확인한 사실 |
|---|---|
| `BlePackagingDevice.rgbOpen(Z)` (`0x383034`) | payload 5바이트 = `[on?FF:00, **01**, on?01:00, appType, appVersion]`. 길이 override 없이(`null`) `sendCmd` 호출. `isColorfulSyncLamp`이면 별도 `cslOpen` |
| `E1Achieve.achieve` (`0x367868`) | 기본 배열 `7E len cmd FF FF FF FF 00 EF`, payload를 3번 위치부터 최대 7번까지 복사. 암호화 boolean이 참이고 명령이 ON_OFF/MODE/BRIGHTNESS면 `AA … 55`로 바꾼 뒤 암호화 |
| `E1Achieve.protocolLen` (`0x367830`) | BRIGHTNESS=4, DATA_TIME=6, 나머지(ON_OFF 포함)=7 |
| `BlePackagingDevice.dataFrom` | 암호화 boolean은 명령과 무관한 **장치 필드 `isEncryptedDevice`** |
| `BlePackagingDevice.brightness` | 같은 `sendCmd` 경로. 차이는 `getLenField()` 길이 override뿐 |

이전 문서의 "두 번째 값 `00`"은 잘못 읽은 것이다. 실제는 상수 `01`이다.
밝기와 전원은 같은 장치 객체·같은 분기·같은 암호화 필드를 쓴다. 실측 밝기 120개가 모두 평문 `7E…EF`였으므로
이 조명은 `isEncryptedDevice=false`이고 전원도 평문이다.

| 동작 | 프레임 (정적 확인) |
|---|---|
| ON | `7e 07 04 ff 01 01 02 01 ef` |
| OFF | `7e 07 04 00 01 00 02 01 ef` |

공개 ELK-BLEDOM 자료에 흔한 `7e 04 04 f0 00 01 ff 00 ef` 형태와는 다르다. 이 앱 분기에서는 위 형태다.
남은 가정은 이 조명이 ColorfulSync 장치가 아니라는 것 하나다(RGB·밝기 실측이 일반 경로 형식과 같아 가능성 높음).
AGENTS 규칙대로 모의 전용으로만 쓴다. 정적 코드 근거이며 대상 장치 HCI와의 실측 대조는 아직이다.

## 4. 남은 증거 정리

차량에서 해야 할 조작은 모두 이미 수행됐다. 아래는 조작이 아니라 **증거의 빈틈**이다.
현장 재확인은 PC 분석으로 답하지 못할 때만 [확인표](../NEXT_PARKED_VISIT.md) 기준으로 정한다.
